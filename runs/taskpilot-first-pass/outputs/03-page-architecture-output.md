# TaskPilot Homepage Architecture — First Pass

## 1. Homepage job
Help a founder, operator or small-team lead quickly recognize that TaskPilot is for the execution gap between planning and follow-through.

The page should create enough clarity and trust to make the visitor want to see how TaskPilot works or try it.

## 2. Primary audience
- founders
- operators
- small-team leads

## 3. Visitor state on arrival
The visitor probably already has task tools, project boards or planning habits.
They do not think they need another list.
They think something important keeps slipping, but they may not have named the problem clearly yet.

## 4. Core message to land first
The problem is not planning.
The problem is keeping important work moving once execution gets messy.

## 5. Supporting messages
- TaskPilot helps protect momentum
- it helps surface slippage earlier
- it reduces status-chasing and coordination drag
- it is for people who already have tools but still lack execution clarity

## 6. Trust question the page must answer
Why is this meaningfully different from a task manager, project board or existing workflow tool?

## 7. Sections the homepage likely needs
1. hero: execution-gap framing
2. problem recognition: where momentum gets lost
3. what TaskPilot helps you see or do
4. how it fits with existing work habits/tools
5. credibility / trust layer
6. CTA / next-step section

## 8. Proof burden per section
- hero: clear pain recognition, no inflated claim
- problem section: concrete examples of slippage and coordination drag
- product section: enough mechanism clarity that the product does not feel imaginary
- fit section: reassurance that this is not just another list
- trust section: honest limitation or believable framing in place of fake proof
- CTA section: low-friction next step

## 9. Risks if the page stays too abstract
- sounds like generic productivity software
- sounds like pure concept branding
- does not explain what the product actually does
- fails the "why this, not my current tool?" test

## 10. Constraints for the draft step
- do not write as if proof already exists
- do not overclaim mechanism
- keep the page anchored in momentum, slippage and coordination drag
- make the difference from generic task tools legible

## Short verdict
This is strong enough to support a first homepage draft.
The page job is clear.
The remaining risk is still mechanism clarity, so the draft step needs to stay disciplined.

## What felt strong
- clear homepage job
- clear visitor state
- clear trust question
- section structure is useful, not bloated

## What still feels weak
- exact product mechanism still thin
- trust/proof section will need careful handling

## Is this strong enough to advance?
Yes.
Proceed to proof mapping and homepage draft, with caution.
