# TaskPilot Wedge Definition Brief

## Why this source exists
The first signal-doc pass exposed a real problem:
we can describe the category, but we still cannot describe the sharp product wedge with enough confidence to write a strong homepage.

This source exists to force a clearer point of view.

## Working decision
For this run, TaskPilot should be treated as:

**a tool for people who are not failing because they do not have tasks, but because the important work keeps losing momentum across too many moving parts**

## First audience hypothesis
Primary:
- founders
- operators
- small-team leads

These are people who already have lists, tools and plans.
The pain is not "I need a task list."
The pain is:
- priority drift
- dropped follow-through
- too much coordination overhead
- too much time spent checking what is moving vs blocked

## Stronger pain framing
TaskPilot is most useful if it speaks to this tension:

**work is not breaking because people forgot to make a list.
It is breaking because momentum gets lost between planning and execution.**

That is a much sharper homepage direction than generic productivity software language.

## Working product implication
TaskPilot should probably be framed less like:
- personal task capture
- generic project management
- AI productivity helper

And more like:
- a way to keep the right work moving
- a way to see what is slipping before it becomes a problem
- a way to reduce status-chasing and coordination drag

## Homepage implication
The homepage should likely optimize for:
- momentum
- clarity
- follow-through
- less coordination drag

Not for:
- feature sprawl
- broad team-software claims
- generic productivity language

## Claims we still cannot make
- exact feature claims
- automation claims
- quantified productivity gains
- deep enterprise coordination claims

## Why this source is useful
Even if some details are still provisional, this source creates a sharper wedge.
That should make the next signal-doc pass materially better.
